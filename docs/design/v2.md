# Version 2 design

**Status:** design only. Nothing here is built yet. This document explains
*what* V2 adds and *how* it fits the V1 architecture, so the work can be split
up and reviewed piece by piece.

V2 has four parts:

1. [PCA visualisation of ancient-genome data](#1-pca-visualisation)
2. [Etymological database with sound changes](#2-etymological-database-with-sound-changes)
3. [Contributor and moderation workflow](#3-contributor-and-moderation-workflow)
4. [Citation-graph visualisation](#4-citation-graph-visualisation)

## Principles carried over from V1

- **Data first.** Everything the site shows comes from files in `data/`, checked
  by the validator. No hand-written HTML content.
- **Static hosting.** The site stays free to host on GitHub Pages, with no
  server or database. Anything that seems to need a server must use GitHub
  itself instead.
- **Every new data type gets a schema, validator rules and tests** before any
  page that displays it.
- **Labels stay honest.** New kinds of evidence get their own evidence level,
  rather than borrowing a stronger one.

## 1. PCA visualisation

The scientific plan (data, sample selection, quality filters, sensitivity
checks, ethics) is in the [pre-registered analysis plan](../genetics/v2-analysis-plan.md).
This section covers how it plugs into the repository and site.

### Where things live

```
analysis/genetics/
  Makefile                 one command runs the steps below, in order
  environment.yml          pinned software versions (EIGENSOFT, ADMIXTOOLS 2, Python)
  DATA.md                  AADR release number, file checksums, usage terms as read
  01_download.py           fetch the release, verify checksums (into a git-ignored folder)
  02_select.py             choose individuals from the .anno table; log every exclusion
  03_pca.par               smartpca settings (lsqproject: YES, …)
  04_export.py             write the small output files below
  outputs/                 committed: small, reviewable results
    pca_main.json
    pca_sensitivity_*.json
    selection_log.csv
data/analyses/
  pca-south-central-asia.yaml   metadata about the analysis, as a citable record
```

The raw genotype data is never committed. Only small derived outputs are, and
only if the AADR's terms allow publishing per-individual coordinates. Otherwise,
group averages only.

### Output format (`pca_main.json`)

```json
{
  "analysis": "pca-south-central-asia",
  "aadr_release": "vNN.N",
  "axes_defined_by": ["present-day group labels…"],
  "variance_explained": [0.0, 0.0],
  "individuals": [
    {"id": "I1234", "group": "Group_Label", "kind": "ancient",
     "date_bp": 3500, "date_method": "radiocarbon", "site": "…",
     "lat": 0.0, "lon": 0.0, "pcs": [0.01, -0.02, 0.003, 0.0],
     "publication": "narasimhan-2019", "flags": ["outlier"]}
  ]
}
```

`publication` must be the ID of a file in `data/sources/`. The validator gains a
rule (**G1**) that checks this, so every dot on the plot traces back to the
paper that produced it.

### A new evidence level

```yaml
- id: project-analysis
  label: Project analysis (not peer reviewed)
  short: PROJ
  max_strength: moderate
```

Claims can cite an analysis record (`data/analyses/*.yaml`) with this level. The
cap means the project's own analysis can never be the only reason a claim is
rated strong.

### The page (`genetics/pca.html`)

- A scatter plot drawn in SVG with plain JavaScript (no new framework), about
  1–3 thousand points.
- Present-day samples as small grey dots; ancient groups in colour, with
  shapes for period. Colour is never the only signal.
- Hover or focus a dot to see its group, date, site and source paper (with a link).
- Filters for period, region and source paper, sharing the existing filter bar.
- A toggle for the main analysis and each sensitivity check.
- A fixed caption: *"PCA shows genetic similarity, not identity or language.
  Positions depend on which samples are included."*
- A table view of the same data, for screen-reader users and for checking.

## 2. Etymological database with sound changes

V1 shows *that* words correspond. V2 shows *why*: the regular sound changes
that turned an ancestral word into each attested form.

### New data: sound changes

`data/linguistics/sound-changes/<id>.yaml`:

```yaml
id: pashto-d-to-l
title: Older *d becomes l in Pashto
language: pashto            # where the change happened
from: "*d"
to: "l"
environment: word-initially and between vowels (to be confirmed)
relative_date: before the earliest Pashto texts
status: unverified
explanation: >
  Plain-language description with examples.
sources:
  - source: morgenstierne-2003
    locator: introduction, § on consonants (to be checked)
examples:                   # must point at existing cognate-set forms
  - set: daughter
    form: lūr
  - set: ten
    form: las
counterexamples: []         # words where the change seems not to apply, and why
```

### Changes to cognate sets

- `proto` (already in the V1 schema) becomes common: the reconstructed form,
  with a source.
- Each form can list the sound changes that derive it from the proto-form, in
  order:

```yaml
- language: pashto
  form: las
  derivation: [pashto-d-to-l]
```

### Validator rules (new)

- **E1:** every example and derivation step points to an existing set, form and sound change.
- **E2:** a sound change marked verified needs a verified source, the same as R6.
- **E3:** a sound change with fewer than two examples is shown as "proposed", not "regular".

### Pages

- **One page per sound change:** the explanation, a table of examples and
  counterexamples, and sources.
- **The cognate table** gains a "show derivation" view. Clicking a form shows
  the chain from proto-form to attested form, step by step, each step linked
  to its sound-change page.
- **One page per language,** listing the changes characteristic of it. This is
  where the "Eastern vs Western Iranian" question becomes visible, since the
  shared changes are the evidence for grouping.

### Scope note

Sound-change histories are specialist work and often debated. Every change
starts `unverified`. Rival analyses are entered as separate sound-change files
linked with `competes-with`, the same pattern as claims.

## 3. Contributor and moderation workflow

**Constraint:** GitHub Pages has no server, so no logins or database on the
site itself. **Approach:** use GitHub as the account and moderation system.
Every contributor already has a GitHub identity, and pull requests already
provide review, history and discussion.

### Roles

| Role | Can do | How it's set up |
|---|---|---|
| Contributor | Propose any change via pull request or issue form | Anyone with a GitHub account |
| Reviewer (per area) | Approve pull requests in their area | `.github/CODEOWNERS`: genetics, linguistics, history, code |
| Maintainer | Merge; manage labels, roles and Code of Conduct reports | Repository admin |

`CODEOWNERS` routes each pull request automatically. For example, changes to
`data/linguistics/` request a linguistics reviewer.

### Contributing without git: issue forms that become pull requests

1. A new issue form, **"Add a claim"**, collects the statement, sources,
   locators and evidence level in structured fields.
2. A GitHub Action reads the submitted form, writes a draft
   `data/claims/<id>.yaml`, runs the validator, and opens a **draft pull
   request** that links back to the issue. If validation fails, it comments
   on the issue with the error messages in plain language.
3. A reviewer takes it from there, as with any pull request.

This gives non-programmers a "submit form" experience while keeping every
change reviewable in git.

### Verification as a recorded act

- `checked_by` must be a GitHub username.
- **New CI check (V1):** in a pull request that sets an entry to `verified`,
  `checked_by` must be someone *other than* the person who added the entry.
  The workflow compares it against the git history of that file. No one
  verifies their own claim.
- Each source and claim page shows its verification history (who, when, what
  was checked), generated from the file's git history and `verification` fields.

### Credit

A generated **Contributors** page lists everyone who has added, reviewed or
verified entries, taken from git history and `contributors` fields, so verification
work gets the same visible credit as writing.

### Moderation tools

- Labels: `needs-source`, `needs-verification`, `contested`, `code-of-conduct`.
- Saved replies for common review feedback, such as "please add a locator" or
  "this evidence level doesn't fit".
- Code of Conduct reports are handled privately, as described in
  `CODE_OF_CONDUCT.md`.

## 4. Citation-graph visualisation

### Purpose

Show how the atlas's knowledge hangs together, and where it's fragile:

- Which claims rest on a **single source**?
- Which sources support **many** claims, so that an error there would spread
  furthest?
- Where are the **contested** clusters, and what evidence does each side use?

### Data

The build already computes everything needed. It will add one more output file,
`graph.json`:

```json
{
  "nodes": [
    {"id": "claim:lost-tribes-descent", "type": "claim", "strength": "contested", "status": "unverified"},
    {"id": "source:dorn-1829", "type": "source", "status": "unverified"},
    {"id": "cognate:daughter", "type": "cognate-set"},
    {"id": "doc:genetics/methods", "type": "doc"}
  ],
  "edges": [
    {"from": "claim:lost-tribes-descent", "to": "source:dorn-1829", "kind": "cites",
     "evidence_level": "oral-tradition", "relation": "supports"},
    {"from": "claim:lost-tribes-descent", "to": "claim:pashtuns-steppe-ancestry",
     "kind": "competes-with"}
  ]
}
```

### The page (`graph.html`)

- A force-directed network diagram drawn in SVG. A small physics simulation
  places connected nodes near each other. It's written in plain JavaScript,
  or with a small vendored library, following the same approach as Leaflet in V1.
- Node shape shows the type (claim, source, word set, doc). Edge colour shows
  the evidence level and line style shows the relation: solid for supports,
  dashed for contradicts, dotted for context.
- Clicking a node highlights its neighbours and shows a summary panel with a link.
- Ready-made views:
  - **Single points of failure:** claims with only one supporting source.
  - **Most-cited sources:** sources ranked by how many claims depend on them.
  - **Contested clusters:** contested claims, their rivals, and the evidence on each side.
  - **Unverified backlog:** coloured by verification status. Doubles as a to-do list.
- A text alternative: the same information as sortable tables.

### Metrics shown on the Method page

- Share of claims verified.
- Share of claims with at least two independent supporting sources.
- Number of contested claims, and how many have evidence on both sides.

## Suggested order of work

| Milestone | Contents | Depends on |
|---|---|---|
| 2.0 | Verification history, "no self-verification" CI check, Contributors page, CODEOWNERS | — |
| 2.1 | Citation graph and fragility metrics | build model (exists) |
| 2.2 | Sound-change data, validator rules E1–E3, sound-change pages | cognate sets (exist) |
| 2.3 | "Add a claim" issue form → draft pull request automation | 2.0 |
| 2.4 | AADR PCA pipeline, `project-analysis` evidence level, PCA page | genetics plan; outside review |

The genetics work comes last on purpose. It needs the most review, and it
benefits from the verification workflow being in place first.

## Open questions

- Do the AADR terms allow publishing per-individual PC coordinates? This
  decides between an individual-level and a group-level PCA page.
- Which transliteration standard should sound-change pages follow for Pashto
  and Avestan? Contributors need one consistent convention.
- Should the issue-form automation be limited to approved contributors, to
  limit spam pull requests?
- At what size does in-browser search need a prebuilt search index?
  Probably beyond a few hundred claims.
